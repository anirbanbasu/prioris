# Shared: Core MCP Tool Contracts

Referenced by `discuss`, `quick-read`, `quiz-me`, and `reading-log`. Assumes a companion MCP server (the `prioris-mcp` server, https://pypi.org/project/prioris-mcp/) exposing at minimum:

## A note on failures

Every tool below fails by raising an opaque `ToolError` with a human-readable message only — as of `prioris-mcp` 0.2.0 (unchanged since 0.1.1) there is no structured, machine-readable error code in the response to branch on programmatically. The code-styled labels used throughout this doc (`not_found`, `invalid_request`, `file_too_large`, `format_unavailable`, ...) are informal shorthand for the failure condition, not something present in the actual response — recognize each case from the error message's content, not by matching a code.

**arXiv** (driven via `shared/scripts/manage_arxiv.py` rather than called directly, for search/list-top-n/fetch-metadata/categories - see `scripts/README.md`)
- `research_arxiv_search(query, max_results=10, start=0, sort_by?, sort_order?) -> results[]` (each: `arxiv_id, title, abstract, authors[{name, affiliation}], categories, primary_category, published, updated, pdf_url, doi?, journal_ref?, comment?`)
- `research_arxiv_fetch_metadata(arxiv_ids: []) -> {results: [...], not_found: [...]}`
- `research_arxiv_fetch_full_text(arxiv_id, format: "pdf"|"html") -> {location, format, size_bytes, served_from_storage, resource_uri}` — callers should try `format: "pdf"` first and retry with `"html"` only on failure; see `agents/document-reader.md`'s "How to fetch and parse" for the actual sequencing every skill relies on (all fetches go through that agent, not called directly).
- `research_arxiv_parse_full_text(arxiv_id, format, offset=0, limit=None, page=None) -> {markdown, offset, limit, total_length, has_more, total_pages?, page_range?, resource_uri}` — fails `not_found` if the id hasn't been fetched first. Paginated — see "Paging through full text" below, including the alternative `page`-based access mode.
- `research_arxiv_list_top_n(include_categories, n, exclude_categories?) -> results[]` — most recent items across one or more arXiv taxonomy codes (`include_categories` combined with AND, optional `exclude_categories` combined with ANDNOT), e.g. `cs.CL`

**Europe PMC** (driven via `shared/scripts/manage_europepmc.py` rather than called directly, for search/fetch-metadata - see `scripts/README.md`)
- `research_europepmc_search(query, page_size=25, cursor_mark="*") -> {results: [...], next_cursor_mark}` (each: `identifier, pmid?, pmcid?, doi?, title, abstract?, authors[{full_name, first_name, last_name, initials}], journal, pub_year, is_open_access, license?, full_text_available`)
- `research_europepmc_fetch_metadata(identifiers: []) -> {results: [...], not_found: [...]}`
- `research_europepmc_fetch_full_text(identifier) -> {location, format: "xml", size_bytes, served_from_storage, resource_uri}` — fails `format_unavailable` if Europe PMC doesn't host full text for this item
- `research_europepmc_parse_full_text(identifier, offset=0, limit=None) -> {markdown, offset, limit, total_length, has_more, resource_uri}` — fails `not_found` if the id hasn't been fetched first. Paginated — see "Paging through full text" below.

**Local filesystem** (see `local-file-handling.md` for the `@file` workflow this backs — no search, metadata, or identifier-resolution capability exists for this source, only these calls)
- `research_localfile_fetch_full_text(content_base64, filename=None) -> {id, location, format, size_bytes, served_from_storage, resource_uri}` — takes the caller's own PDF bytes, base64-encoded, not a path: there is no server-side filesystem to resolve against, so this works identically under stdio and streamable-http/http transports. There is no `format` input — only PDF is accepted, so the output's `format` is always `"pdf"`. `filename` is an optional hint stored for reference only, never used to derive identity or location. Fails `file_too_large` if the encoded payload's length alone implies it would exceed the server's configured size ceiling (checked before decoding), again post-decode in case base64's rounding slipped a couple of bytes past that pre-check, `invalid_request` if `content_base64` doesn't decode as valid base64, and `invalid_request` if the decoded bytes don't sniff as a PDF (checked by magic-byte prefix, not by trusting a `.pdf`-looking filename). `id` is a caller-facing identifier this call mints (or, if the exact same file content was already fetched, the existing one) — opaque, derived from a hash of the decoded content, not from `filename`. Always re-decodes and re-hashes the given bytes fresh on every call — never assume a previously-returned `id` still corresponds to the file's current on-disk content without re-reading and re-sending it first. **Deprecation candidate**: the whole payload must fit in one call, which risks exceeding transport-level body size ceilings for anything but small files — `local-file-handling.md` drives every local file through the chunked-upload flow below instead, via `shared/scripts/pdf_chunk_upload_helper.py`, and this tool is not called directly by any skill.
- `research_localfile_begin_upload(filename=None) -> {session_id, max_chunk_bytes}` — starts a new chunked-upload session. `max_chunk_bytes` is the server's current `PRIORIS_MCP_LOCAL_FILE_UPLOAD_MAX_CHUNK_BYTES` ceiling; a caller must size its chunks against this returned value, not a hardcoded guess, since it's a server-side config that can change. Fails `invalid_request` if `PRIORIS_MCP_LOCAL_FILE_UPLOAD_MAX_CONCURRENT_SESSIONS` sessions are already open (checked after sweeping any TTL-expired ones).
- `research_localfile_upload_chunk(session_id, index, chunk_base64) -> {received_index, bytes_so_far}` — appends one chunk. `index` is zero-based and must equal the number of chunks already accepted for this session — chunks are required in strict sequential order, and there's no `total_chunks` parameter; the caller decides when it's done by calling `finalize_upload`. Fails `not_found` if `session_id` is unrecognised or has passed `PRIORIS_MCP_LOCAL_FILE_UPLOAD_SESSION_TTL_SECONDS` since its last chunk; `invalid_request` if `index` isn't exactly the next expected index or `chunk_base64` isn't valid base64; `file_too_large` if this chunk exceeds `max_chunk_bytes` or the running total exceeds the server's overall size ceiling.
- `research_localfile_finalize_upload(session_id) -> {id, location, format, size_bytes, served_from_storage, resource_uri}` — concatenates all accepted chunks and runs the same magic-byte sniff, size check, content-hash canonicalisation, and persistence as `fetch_full_text`, via a shared internal path — identical output shape. Removes the session whether it succeeds or fails: a caller whose finalize fails must `begin_upload` again rather than retrying finalize. Fails `not_found` if `session_id` is unrecognised or expired; `invalid_request` if zero chunks were ever uploaded or the reassembled content doesn't sniff as a PDF; `file_too_large` if the reassembled content exceeds the server's size ceiling.
- `research_localfile_parse_full_text(id, offset=0, limit=None, page=None) -> {markdown, offset, limit, total_length, has_more, total_pages?, page_range?, resource_uri}` — `id` is the caller-facing id `fetch_full_text`/`finalize_upload` returned, not `path`; fails `not_found` if that id was never returned by either. Paginated exactly like the other providers' `parse_full_text` — see "Paging through full text" below, including the `page` access mode. No `format` choice exists for this source (always `pdf`).

**Cross-provider**
- `research_resolve_identifier(identifier, format) -> {identifier, provider, resolved_url, format, full_text_available?}` — resolves an arXiv id, a Europe PMC id/PMCID, or a DOI of unknown provider to its canonical form. Does **not** accept a URL — a bare DOI is resolved via a doi.org redirect (checked against an allowlisted domain before any further request), everything else is self-identifying by pattern with no network round-trip. Standalone utility, not a required first step when the provider is already known. Does not resolve local files — there is nothing to resolve; a local file's identity is its content hash, established only by calling `research_localfile_fetch_full_text` itself.

**Search over fetched content**
- `research_search_fetched(query, provider?, identifier?, format?, mode="fts", offset=0, limit=None) -> {fts?, vector?, index_status}` (driven via `shared/scripts/manage_search.py` rather than called directly) — searches content already fetched *and* parsed on the server; never triggers a fetch or parse itself, so it only surfaces papers some caller (this session or another) already pulled in before. `mode` selects the mechanism: `"fts"` (default, FTS5 syntax — plain keywords, phrase quotes, `AND`/`OR`/`NEAR` all work), `"vector"` (embedding similarity over free text), or `"hybrid"` (both). **Breaking as of `prioris-mcp` 0.2.0**: the result is no longer a flat `{matches: [...]}` — `fts` and `vector` are each their own paged block, `{matches: [{provider, identifier, format, snippet, offset, score}], offset, limit, total, has_more}`, populated only when that mechanism actually ran (`mode` equal to that name, or `"hybrid"`); read `result.fts.matches`/`result.vector.matches`, never a top-level `result.matches`. `index_status` reports every mechanism the running server supports (`"ready"`/`"stale"`/`"not_built"`/`"building"`), regardless of which single `mode` was requested — check it before trusting a `vector`/`hybrid` result is complete. Vector/KNN search is **unthresholded**: it always returns up to `limit` nearest matches regardless of how dissimilar they are, so treat `score` as a relevance signal to filter on client-side, never assume every match is relevant. `offset`/`limit` apply per mechanism, not globally. Optionally scoped to one `provider`, one `(provider, identifier)` pair (`identifier` requires `provider`), and/or one `format` — `identifier` scopes the search to one document, it doesn't look that document up on its own; `query` is still required (FTS5 syntax for `mode="fts"`, free text to embed otherwise). Matches don't carry `title`/`authors` — enrich via `shared/scripts/metadata_cache.py read <provider> <identifier>` where a cache entry exists. See `discuss`'s local-search-first step for how this is used in practice.

**External discovery** (driven via `shared/scripts/manage_discovery.py` rather than called directly, for discovery search - see `scripts/README.md`)
- `research_discovery(query, max_results?, page=1, from_year?, to_year?, open_access_only=false) -> {hits: [<DiscoveryHit>, ...], page, per_page, total, has_more}` — finds external candidates *not already in the local corpus*, ranked by OpenAlex's `search.semantic` embedding similarity to `query` (free text — title, abstract, grant summary, or similar, up to 2000 characters); never fetches, parses, or persists anything itself. `max_results` defaults to `PRIORIS_MCP_DISCOVERY_MAX_RESULTS`; `page` is 1-indexed, within `search.semantic`'s own hard 50-match cap — `total` reflects OpenAlex's own total-match count for the query (capped at 50), not the post-exclusion `hits` list, so a page can come back with fewer than `per_page` hits (already-fetched candidates filtered out) even though `has_more` is still `true`. `from_year`/`to_year` filter by publication year; `open_access_only` restricts to works OpenAlex marks open access.

  Each `DiscoveryHit` is `{openalex_id, title?, abstract?, authors: [{name}], publication_year?, doi?, work_type?, score, fetch_route}` — `work_type` is one of `research://openalex/work-types`'s codes; `score` is OpenAlex's own embedding-similarity score, not comparable across separate calls. `fetch_route` is `{kind: "known_provider"|"oa_link"|"manual_upload", provider?, identifier?, pdf_url?}`: `"known_provider"` sets `provider`/`identifier` for a direct `research_arxiv_fetch_full_text`/`research_europepmc_fetch_full_text` call; `"oa_link"` sets `pdf_url`, an open-access PDF URL; `"manual_upload"` means OpenAlex offers no fetch path at all. Wired into `discuss`'s Provider search step (see `skills/discuss/SKILL.md`) as a fourth, single-call search option alongside arXiv/Europe PMC — by design, `oa_link`/`manual_upload` hits are surfaced there as a link/DOI for the user to follow themselves; there is deliberately no automated download path for either, and none is planned.

**Resources** (read-only; never trigger a fetch or parse — read one that doesn't exist yet and you get a plain not-found, not an error):
- `research://{provider}/{identifier}/{format}/fulltext` — persisted raw full text, returned whole (not paginated)
- `research://{provider}/{identifier}/{format}/markdown{?offset,limit,page}` — persisted parsed markdown, one page at a time: `{markdown, offset, limit, total_length, has_more, total_pages?, page_range?}`. Paginated identically to `parse_full_text` below (same params, same shape minus `resource_uri`, since the read is already keyed by that URI).
- `research://arxiv/categories` — arXiv's queryable category codes and names, returned whole (not paginated). Read this to look up or confirm a taxonomy code (e.g. for `research_arxiv_search`'s `cat:` syntax or `research_arxiv_list_top_n`'s `include_categories`/`exclude_categories`) rather than guessing one from memory.
- `research://openalex/work-types` — OpenAlex's work `type` vocabulary, `{types: [{code, name, description}]}`, returned whole (not paginated). Read this to interpret a `research_discovery` hit's own `work_type` field rather than guessing what a code like `article` covers.
- `research://vector-index/rebuild-status` — in-memory, process-local progress of the server's corpus-wide vector-index rebuild (triggered by a `PRIORIS_MCP_EMBEDDING_MODEL` change at startup), `{documents: {total, pending, succeeded, failed, cancelled, active}, notes: {...}}` for each of the two vector corpora. Not a durable job log — answers whether the rebuild that started when the server process started is still going, nothing more.

In practice you rarely need to read a resource explicitly: `parse_full_text` already returns a `markdown` page inline, plus the `resource_uri` for re-reading it later (e.g. a fresh session, or a different skill) without re-parsing. The two-step fetch → parse pattern is universal across all three sources — always fetch before parse; parse fails `not_found` otherwise.

## Paging through full text

`parse_full_text` (all three sources) and the `.../markdown` resource no longer return the whole document in one call — each call returns one bounded page of Markdown (`offset`, `limit`, `total_length`, `has_more`), capped by a server-side default (currently ~20,000 characters) unless a larger `limit` is passed explicitly. A short paper may fit in a single page (`has_more: false` immediately); a long one won't.

Whoever needs the *complete* text — in practice, always `agents/document-reader.md`, which mediates every full-text touch on behalf of the skills — must loop rather than assume one call is enough:

1. Call with `offset=0` (default), collect `markdown`.
2. While the response's `has_more` is `true`, call again with `offset` advanced by the length of the `markdown` just received (not by `limit` — the last page can be shorter), and append the new `markdown` to what you have.
3. Stop once `has_more` is `false`; concatenate the collected pages in order before treating your view of the text as complete.

This applies the same way whether you're calling `parse_full_text` directly or re-reading a cached paper via its `resource_uri` instead of re-parsing.

`research_arxiv_parse_full_text` and `research_localfile_parse_full_text` (PDF sources only — Europe PMC's XML has no page concept) additionally accept a `page` param: a 1-indexed PDF page to jump to directly, resolved against the document's own manifest, instead of walking `offset` from the start. Passing `page` returns `total_pages` (the document's page count) and `page_range` (the `[first_page, last_page]` the returned slice actually spans) alongside the usual fields — both are `null` for non-page-aware formats/sources. `page` and `offset`/`limit`-based walking are two independent ways to reach the same underlying content, not composable — pick one per call; `document-reader.md`'s current loop uses `offset`-based walking throughout, since it needs the whole document rather than one page.

## Notes

`prioris-mcp`'s `NotesBackend` — CRUD/search over user-authored notes (driven via `shared/scripts/manage_notes.py` rather than called directly), plus a read-only export resource. Unlike everything else on this page, there is no upstream API behind these calls; `NotesBackend` is entirely a `prioris-mcp` design decision. Released as of `prioris-mcp` 0.2.0 (`docs/requirement-specification/06-interface-specification.md#notes` and `storage/02-notes-storage.md`).

A note's full shape: `{"id": <UUID string>, "provider": <string>, "canonical_identifier": <string>, "format": <string|null>, "text": <string>, "anchors": [<Anchor>, ...], "author_name": <string|null>, "tags": [<string>, ...], "metadata": <object[string,string]|null>, "created_at": <ISO 8601>, "updated_at": <ISO 8601>}`. An `Anchor` is `{"location": {"page_number": <int|null>, "section_heading": <string|null>, "paragraph_index": <int|null>} | null, "selectors": {"exact_text_quote": <string|null>, "prefix_context": <string|null>, "suffix_context": <string|null>} | null}` — an entry with both `location` and `selectors` absent (or all-null within them) fails `invalid_request`; anchors are unresolved positional hints, never validated or re-resolved against the paper's own text.

- `research_notes_create(provider, identifier, format?, text, anchors?=[], author_name?=null, tags?=[], metadata?=null) -> Note` — `identifier` is provider-native (not yet canonicalised); resolved to its canonical/pinned form server-side before persisting (skipped when `format` is omitted, e.g. a note predating any fetch). For `localfile`, `identifier` is used as-is (already a stable, server-minted id). Fails `invalid_request` if `provider` isn't `arxiv`/`europepmc`/`localfile`, or any `anchors` entry is fully empty.
- `research_notes_read(note_id) -> Note` — fails `not_found` if no note has this id.
- `research_notes_update(note_id, text?, anchors?, tags?, metadata?) -> Note` — every field is optional; an omitted field is left unchanged (`anchors: []`/`tags: []`/`metadata: {}` are valid, distinct-from-omitted ways to clear those three). `provider`/`canonical_identifier`/`format`/`author_name` cannot be changed by this tool — changing "which document" is a new note, not an edit. Fails `not_found` if `note_id` doesn't exist.
- `research_notes_delete(note_id) -> bool` — `true` if a note was found and removed, `false` if already absent; never an error for an absent id.
- `research_notes_search(provider?, canonical_identifier?, format?, date_from?, date_to?, keyword?, author_filter?="any", author_name?, tags_all?=[], tags_any?=[], tags_exclude?=[], offset?=0, limit?=50, mode="fts") -> {fts?, vector?, index_status?}` — every filter is optional; no filters returns everything, paginated. `canonical_identifier` given without `provider` fails `invalid_request`. `author_filter` is a tri-state (`any`/`mine`/`named`, not a nullable string) since `author_name IS NULL` ("mine") and "no author filter at all" are different queries; `author_name` is only meaningful with `author_filter="named"`, and giving it with any other value fails `invalid_request`. `date_from`/`date_to` filter on `created_at`. `tags_all`/`tags_any`/`tags_exclude` are must-have-every / must-have-at-least-one / must-have-none over the exact-match `tags` list — **not** keyword-indexed. Never triggers a fetch or parse.

  `mode` selects the mechanism, same as `research_search_fetched`: `"fts"` (default — `keyword`, if given, is FTS5 syntax matching `text` only, never `anchors`/`metadata`; default order `created_at` descending, or relevance if `keyword` is given), `"vector"` (`keyword` is required for this mode — fails `invalid_request` ("nothing to embed") otherwise — free text embedded and matched by similarity), or `"hybrid"` (both, `keyword` required to get a `vector` block). **Breaking as of `prioris-mcp` 0.2.0**: the result is no longer a flat `{notes: [...], offset, limit, total, has_more}` — read `result.fts.notes`/`result.fts.offset`/etc, never top-level fields. `fts` is `{notes: [<Note>, ...], offset, limit, total, has_more}`; `vector` is `{matches: [{note_id, score, text_preview}], offset, limit, total, has_more}` — only `note_id`/`score`/`text_preview` per match, re-read the full `Note` via `research_notes_read(note_id)` if more is needed. Each of `fts`/`vector` is populated only when that mechanism actually ran. `index_status` is present only when a vector search ran, and reports the vector mechanism's status across every note matching this call's *structural* filters as a whole (not just the notes on this page) — `"not_built"` if that filtered scope is empty. Vector search is unthresholded, same caveat as `research_search_fetched`'s — filter by `score` client-side.
- `notes://{note_id}/export` (resource, read-only) — `{"suggested_filename": <string, the note's own id, already suffixed with ".md">, "frontmatter": <object, every Note field except text>, "markdown_body": <string, exactly the note's text>}`. The server never writes this to a file itself; the caller (see `vault-export`, and `shared/scripts/render_note_export.py`) renders `frontmatter` into whatever dialect its target expects. Reading an id that doesn't exist is a plain not-found, like every other resource on this page.

`metadata` is caller-owned, opaque scratch space: persisted and returned verbatim, never interpreted, and **not filterable or searchable** via `search` — a key that matters enough to filter/search by belongs in `tags` (or a new dedicated field), not `metadata`. See `notes-model.md` for why this plugin's spaced-repetition state deliberately does not use it.

`rmotd` additionally needs `research_arxiv_list_top_n`, documented in its own SKILL.md rather than here since it's the only tool `rmotd` uses.

If an expected `prioris-mcp` tool isn't available in the current session, say so plainly and stop — do not guess at paper content from memory or fall back to a built-in web search/fetch tool as a substitute (see `scope.md`).
