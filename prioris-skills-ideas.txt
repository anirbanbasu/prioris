PRIORIS — SKILL IDEAS DISCUSSION
Date: 2026-07-28
Status: discussion only — nothing here has been implemented.

This is a record of a design discussion about four candidate skills for the
`prioris` plugin, refined through back-and-forth, plus a separate question
about context/token management across a long reading session. Nothing in
this file is a spec; it's the reasoning trail so a future implementation
pass doesn't have to be re-derived from scratch.

================================================================================
1. EXPORT CITATION TO BIBTEX
================================================================================

Decision: extend the cache, don't re-fetch at export time.

The MCP contract (research_arxiv_search / fetch_metadata, and the Europe PMC
equivalents) already returns doi, journal_ref, pub_year, comment as optional
fields. But the current cached frontmatter schema (shared/data-layout.md)
only persists: provider, identifier, title, authors, source_url,
resource_uri, fetched_at, read_at, tags. It does NOT persist doi/journal_ref/
pub_year/comment today.

Chosen approach: extend the frontmatter schema to capture those fields at
fetch time, so a BibTeX export skill is a pure local read — no MCP call
needed at export time. This is a shared/data-layout.md schema change plus a
touch to the Fetch step in both `discuss` and `quick-read` (wherever
.prioris/papers/<provider>/<identifier>.md gets written), not just a new
standalone skill. Bonus: this also makes reading-log recaps richer for free
once it's in place.

Design note: arXiv preprints and Europe PMC published papers want different
BibTeX entry types (@misc/@article with eprint vs. @article with journal/
volume/pages) — this maps cleanly onto the plugin's existing per-provider
tool split rather than fighting it.

================================================================================
2. EXPORT TO DOCX / PPTX USING AN EXISTING TEMPLATE
================================================================================

Initial concern: the plugin's whole identity is "will not draft, outline, or
write any part of a manuscript." A templated document/deck export risks
sliding from "reformat what's already written" into "compose new content to
fill placeholders."

Refinement after discussion: the real use case is legitimate and narrower
than manuscript drafting —
  - DOCX: an executive-summary one-pager from already-recorded discussion /
    quick-read notes.
  - PPTX: a management-facing explainer deck — genuinely useful for
    communicating what a researcher is actually doing to a non-technical
    audience, even though PPTX is a worse tool than LaTeX Beamer on the merits.

The sharpened rule (this is the important part): the skill may SIMPLIFY,
REFRAME, and CUT JARGON for the stated audience, but every claim on the
page/slide must trace back to something already present in a cached
discussion/quick-read note. No new analysis, no filling gaps the paper (or
the recorded discussion of it) didn't cover. "No new prose at all" was too
strict a rule — this one (no new CLAIMS) is the right boundary and should be
written explicitly into whatever skill gets built here.

Open design question: format (docx/pptx/pdf) and audience/distillation level
(full technical note vs. simplified one-pager) are actually two independent
axes. The natural default pairing is DOCX = exec-summary, PPTX = management
deck, but that shouldn't be hard-coded — someone may eventually want a
technical PPTX for a lab meeting, or a full-text DOCX. Treat both as
parameters, with the DOCX/exec + PPTX/management pairing as the sensible
default when neither is specified.

================================================================================
3. EXPORT DISCUSSIONS AS PDF (VIA PANDOC)
================================================================================

Agreed: (2) and (3) are the same underlying export mechanism — take existing
cached markdown, run it through pandoc with a template:
  - DOCX/PPTX: `pandoc --reference-doc=template.{docx,pptx}` applies the
    template's styles without any new Python dependency (python-docx /
    python-pptx / docxtpl not needed — keeps the plugin's "shell out to one
    well-known tool" pattern rather than adding a library surface).
  - PDF: pandoc's PDF path needs a LaTeX engine (or wkhtmltopdf/weasyprint) —
    a much heavier dependency than `uv`/`uvx`. Should be documented as an
    optional "Requires" addition with a graceful fallback ("pandoc/LaTeX not
    found — here's the markdown instead") rather than a hard failure.

Given the shared mechanism, consider whether this is really one `export`
skill with a format argument, rather than three separate skills — fewer
places for the "no new claims" scope language to drift out of sync.
BibTeX doesn't fit this shape (structured-data generation, not document
rendering via pandoc), so it stays separate either way.

================================================================================
4. CROSS-POLLINATION ACROSS DISCUSSIONS
================================================================================

The README already flags this as a deliberately deferred feature ("cross-
paper synthesis... to be built later on top of the same markdown store").

Key insight from this discussion (worth keeping, it's sharper than the
existing scope boundary): the real risk of open-ended cross-pollination
isn't "drafting a manuscript" — it's the LLM ORIGINATING an idea that the
researcher then unknowingly treats as their own. That's a provenance/
authorship-integrity risk, distinct from (and arguably more important than)
the existing "no manuscript prose" rule. Worth stating as its own principle
alongside shared/scope.md's existing boundary:

  "This plugin evaluates and grounds ideas the researcher supplies; it does
  not originate hypotheses or claims on its own initiative."

Given that principle, the reframed ask is NOT "synthesize connections across
my reading for me" (risky — LLM originates) but "help me dig further into an
idea I already have, using what I've cross-cached" (safe — LLM grounds,
researcher originates). Structurally this is `discuss`'s core interaction
loop (one paper vs. the user's stated idea) generalized to N cached
DISCUSSION NOTES (not full papers — same "keep it cheap" principle
reading-log already follows). The user supplies the idea; the skill's job is
to say what supports it, contradicts it, or is missing, grounded in already-
cached notes, never inventing connections that don't trace to those notes.

Open question before this becomes a dedicated skill: how much of this is
already covered by reading-log's filters (find the relevant cached notes)
followed by ordinary conversation? The genuine gap a dedicated skill would
close is (a) formalizing the "ground, don't originate" contract explicitly
rather than relying on ad hoc conversation discipline, and (b) optionally
persisting the resulting exploration to disk (a new .prioris/ subfolder?) the
way `discuss` persists its notes. If neither of those matters, this may not
need to be a skill at all — just a habit of chaining reading-log into
conversation.

--------------------------------------------------------------------------------
`compare` skill (refined, distinct from the above)
--------------------------------------------------------------------------------

Refined definition: `compare` takes the RESEARCHER'S OWN SPECIFIED CRITERIA
across a handful of NAMED papers (bounded set) — e.g. "compare these three
papers on sample size, statistical power, and reproducibility" — and
produces a structured side-by-side breakdown.

This is a clean complement to the "dig deeper" idea above, not a
duplicate:
  - `compare`:    criteria-driven, closed/named paper set, side-by-side.
  - "dig deeper": idea/hypothesis-driven, open paper set (whatever's
                  relevant in the cache), exploratory grounding.

Both hand the FRAME to the researcher (criteria, or idea) and keep the model
in a strictly evaluative role — i.e., both are applications of the same "no
origination" principle, just along different axes (fixed-criteria/fixed-set
vs. open-idea/open-set).

================================================================================
5. TOKEN / CONTEXT MANAGEMENT ACROSS A LONG READING SESSION
================================================================================

Question raised: reading many papers in one continued session will explode
token count even though each skill is individually designed to be cheap
(discuss/quick-read/quiz-me deliberately hold only one paper's full text at a
time — but across many invocations in one session, earlier full-text loads
don't disappear from the conversation history on their own).

Verified against current Claude Code documentation (not assumption):

1. An agent/skill CANNOT programmatically trigger /compact (or equivalent
   compaction) on itself. There is no "Compact" tool exposed to the agent
   tool-calling surface. Compaction is host/user-invoked only — either the
   user runs /compact, or the platform's automatic compaction kicks in.

2. There is a PreCompact hook, but it is REACTIVE, not proactive: it fires
   right before compaction begins (trigger: "manual" or "auto") and can only
   BLOCK compaction (decision: "block" / exit code 2) — it cannot initiate
   compaction or watch context size and trigger early. No threshold-based,
   plugin-driven compaction exists.

3. The only user-facing compaction control is `autoCompactEnabled` (default:
   true) — an on/off switch. There is no documented setting to make
   auto-compact trigger earlier or more aggressively; the threshold itself
   isn't configurable.

4. A skill CANNOT force or compel the user to run /compact. The only
   available mechanism is suggestion: a skill's own text output can
   recommend it, nothing more.

Implication for this plugin: "force the user to compact" isn't something a
skill can implement — full stop. What's actually available:

  - Rely on the platform's automatic compaction (autoCompactEnabled) — this
    already partially addresses the concern without any plugin work.
  - Have full-text-heavy steps (the point in `discuss`/`quick-read` right
    after fetching full text) end with an explicit, human-readable nudge:
    something like "Full text is now in context. Since everything useful
    from this discussion has already been saved to
    .prioris/discussions/<provider>/<identifier>.md, running /compact — or
    starting a fresh session — before moving to a different paper will keep
    context lean without losing anything."
  - The strongest mitigation isn't compaction at all: because every skill
    already persists what matters to `.prioris/` as small markdown files,
    STARTING A NEW SESSION per paper (or per few papers) is essentially
    free — nothing is lost, unlike compaction which is lossy/summarizing.
    This is worth stating as the recommended practice, with /compact as the
    fallback for people who prefer to stay in one continuous session.

No skill can enforce any of this; at most, SKILL.md instructions can carry
the suggestion consistently at the right moment in each workflow.

================================================================================
OPEN QUESTIONS / FOLLOW-UPS
================================================================================

- (1) BibTeX: decide exact frontmatter field names/shape before touching
  shared/data-layout.md and the two Fetch steps that write it.
- (2)/(3) Export: decide single `export` skill (format + audience params) vs.
  keeping them logically separate; source template files need a documented
  location convention (e.g. a user-provided path vs. a bundled default).
- (4) "Dig deeper": decide whether the reading-log-plus-conversation path is
  actually insufficient before building a dedicated skill; if built, decide
  whether/where results get persisted.
- (4) `compare`: bounded N — how many named papers is reasonable before this
  starts needing the same "keep it cheap" discipline as everything else?
- New principle ("no idea origination") — consider adding to shared/scope.md
  alongside the existing manuscript-drafting boundary, since it now applies
  to more than just idea (4).
